# P09 — الصيانة والوقاية في المرحلة الأولى

## النطاق المنفذ

التغيير محصور في صفحة الصيانة والوقاية ومساعدات خدماتها ووحدة انتقالات جديدة:

- `client/src/pages/services/OperationsServices.tsx`
- `client/src/pages/services/shared.tsx`
- `client/src/lib/prototype-maintenance.ts`
- `client/src/lib/prototype-maintenance.spec.ts`

لم تُعدّل ملفات السياق أو التنقل أو العقارات أو دورة العقد أو المالية. تبقى الخدمات المؤجلة تحت بوابة المرحلة التي يملكها الفريق الأب؛ لم تُوسّع وظيفتها هنا.

## عقد العلاقة والنطاق

لا تقبل نماذج الصيانة أو الوقاية قيمة «كل المحافظ» ولا اسم وحدة حرًا كرابط. يبدأ النموذج باختيار `propertyId` صريح، وتستخلص العملية `portfolioId` من العقار نفسه. الوحدة اختيارية، لكن إن اختيرت ترسل `unitId` فقط ويجب أن تتبع العقار والمحفظة المستخلصين؛ أي علاقة ناقصة أو متعارضة تُرفض قبل إنتاج حالة جديدة.

`scopedForm` يضع خيارًا فارغًا صريحًا قبل العقار والوحدة، فلا تختار `FormDialog` أول محفظة أو أول عقار بالنيابة عن المستخدم. القيمة تظل موجودة في الحوار عند رفض التحقق لأن الحوار المشترك القائم يمسك الاستثناء ولا يغلقه؛ ولم يتغير سلوك Escape أو حبس التركيز أو إعادة التركيز الخاص به.

هذا ينطبق كذلك على الدورية الوقائية الموجودة. الوصف النصي للدورية ليس رابط عقار أو وحدة.

## دورة طلب الصيانة

تعمل العمليات الصرفة من `prototype-maintenance.ts` مع `commitTransition` للمشغّل:

1. `createMaintenanceRequest` ينشئ طلبًا واحدًا في العقار/المحفظة الصحيحة، بحالة `طلب جديد` وتاريخ المجال `scenarioDate(state)`.
2. `submitMaintenanceForReview` ينقله إلى `بانتظار اعتماد` ولا ينشئ تكلفة أو مصروفًا أو نقدًا.
3. `approveMaintenanceRequest` يتحقق من معاينة دور `owner` فقط. واجهة المالك تستخدم استثناء الحالة فقط الموجود في `PrototypeContext` لتطبيق `معتمد`؛ لا تمنح تحريرًا عامًا ولا تستدعي `commitTransition` المخصص للمشغّل.
4. `linkMaintenanceCost` يربط تكلفة موجبة غير قابلة للاستبدال بعد الاعتماد، مع تاريخ المصروف والتصنيف والفئة، لكنه لا ينشئ مصروفًا أو دفعة.
5. `completeMaintenanceWork` يتطلب الاعتماد والتكلفة المرتبطة قبل الحالة `منجز`.
6. `materializeMaintenanceExpense` ينشئ مصروفًا مستحقًا واحدًا فقط وينقل الطلب إلى `مصروف مستحق`.
7. `payMaintenanceExpense(state, expenseId, paymentDate, paymentMethod, requestId)` هو انتقال التسوية الصريح والمنفصل. يتحقق من تاريخ السداد، ومصروف واحد غير مسدد، وعلاقة `maintenanceId` و`sourceEventId` الثنائية، ومعرف طلب التسوية. ينشئ سجل `payments` محليًا واحدًا فقط بعلامة `externalTransfer: false`، ثم يحدّث المصروف ومرجع الطلب إلى `مسدد`. لا يستدعي مزود دفع أو بنكًا ولا يحدث تلقائيًا عند تغير حالة الصيانة.

العمليات تعيد حالة جديدة كاملة أو ترمي خطأ قبل أي كتابة جزئية. يحمي `requestId` إعادة إنشاء نفس الطلب إذا كانت البيانات متماثلة، ويرفض إعادة استخدامه ببيانات مختلفة. تحفظ العمليات تدقيقًا محليًا بوقت تشغيل فعلي UTC عبر `new Date().toISOString()`؛ تاريخ السيناريو لا يُسمى تاريخ اليوم ولا يستخدم في التدقيق.

## عقد المصروف المالي

إنشاء المصروف هو إثبات استحقاق/فاتورة مورد داخل النموذج، **وليس سدادًا**. لا ينشئ انتقال الإنشاء `payments` أو `collections` أو رقمًا من نوع `INV-DEMO`. حالة المصروف الابتدائية `غير مسدد` و`paymentStatus: غير مسدد`. لا يتحول إلى `مسدد` إلا بعد استدعاء `payMaintenanceExpense` صراحةً؛ عندها ينشأ سجل تسوية محلي واحد، لا تحويل أو قبض أو اتصال خارجي. تعرض واجهة الصيانة رابطًا صريحًا إلى `/expenses` بدل تعديل المصروف مباشرة.

تُحفظ الحقول التي يحتاجها فريق المالية لإعادة الحساب متسقة بين طلب الصيانة والمصروف:

| الحقل          | طلب الصيانة                 | المصروف المستحق                    |
| -------------- | --------------------------- | ---------------------------------- |
| المبلغ         | `meta.costMinor`            | `amountMinor` نفسه                 |
| التاريخ        | `meta.expenseDate`          | `date` و`meta.expenseDate` نفسيهما |
| النوع          | `meta.classification`       | `meta.classification` نفسه         |
| الفئة          | `meta.category`             | `meta.category` نفسها              |
| رأسمالي/تشغيلي | `meta.capex` و`meta.opex`   | القيم نفسها                        |
| مصدر الحدث     | `meta.sourceEventId`        | `meta.sourceEventId` نفسه          |
| علاقة الصيانة  | —                           | `meta.maintenanceId`               |
| النطاق         | `portfolioId` و`propertyId` | القيم نفسها                        |

المعرف المالي ثابت لكل طلب: `sourceEventId = maintenance-expense:<maintenanceId>` و`expenseId = expense-<maintenanceId>`. عند النقر أو إعادة المحاولة، تعيد العملية المصروف نفسه دون إنشاء آخر فقط إذا كان الربط ثنائيًا وكاملًا ومتسقًا. وجود أكثر من مصروف مرتبط، أو مصدر حدث مكرر، أو `expenseId` في الطلب بلا مصروف مطابق، أو مصروف مرتبط بلا `expenseId` مطابق في الطلب، يرفض العملية بدل إصلاحها عبر سجل إضافي.

### تسليم P10b واحتياج واجهة المالية

سُلّمت واجهة الانتقال الصرفة التالية لفريق المالية:

```ts
payMaintenanceExpense(state, expenseId, paymentDate, paymentMethod, requestId);
```

يجب أن تربط صفحة المصروفات، في ملفها المملوك لفريق المالية، هذا الاستدعاء بـ`commitTransition` عند تأكيد المستخدم المحلي فقط، وبـ`requestId` جديد ثابت لطلب الإرسال نفسه. لا يجوز للواجهة أن تستخدم `patch` لحالة المصروف، أو أن تستدعي العملية أثناء إنشاء الصيانة، أو أن تدعي إرسال تحويل خارجي. تعيد المحاولة بالمعرف والبيانات نفسيهما نفس سجل التسوية؛ التغيير في التاريخ/الطريقة أو وجود سداد سابق/علاقة جزئية يرفض العملية. لا يلزم P09 أي مزود دفع أو API خارجي.
